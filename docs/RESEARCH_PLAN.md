# Remedy 研究计划：根据失败设计训练任务

## 研究问题

语言模型 Agent 在长步骤环境中会反复遇到自己的薄弱环节。Remedy 研究：**能否利用 Solver 的真实失败，让 Designer 构造有针对性的可解任务，并用这些任务的正确轨迹持续提升 Solver？**

核心假设是，诊断反馈能帮助 Designer 把训练预算集中到 Solver 尚未掌握的行为上。例如，若 Solver 多次在取物后反复查看背包、没有把物品放到目标容器，Designer 可以构造需要多次取放或区分目标容器的任务。Planner 提供这道题的操作轨迹，Solver 从中学习；下一轮诊断再观察这些行为是否改善。

这是一项待验证的研究假设。生成任务可解、训练能够执行，都不能单独证明根据失败出题比随机出题更有效。最终要通过同预算对照观察独立测试成绩。

## 两个模型角色与环境

- **Solver**：接收任务、当前观察、动作历史、合法动作和剩余步数，选择环境动作。基础权重冻结，训练其 LoRA。
- **Designer**：读取当前 Solver 的诊断反馈和 ALFWorld 的对象与容器兼容规则，生成任务假设及场景规格。当前阶段 Designer 权重冻结。
- **Planner 与 Host**：依据 PDDL 规则求解任务，在真实 Text ALFWorld 环境中重放并验证轨迹；它们提供可验证监督，不承担可训练的模型角色。

当前实现可让两个角色共用 Qwen3‑4B 基础模型。Solver 加载 LoRA 执行与训练；Designer 生成任务时关闭该 adapter，因此 Solver 更新不会修改 Designer 的权重。

## 每轮如何运行

### 1. 诊断当前 Solver

从 ALFWorld `train` 场景抽取诊断任务，运行当前 Solver。记录完整目标、动作和观察轨迹、成功与否、任务进度、重复动作及停滞导航等信息。摘要保留可引用的失败案例与编号，供 Designer 指定本次任务想调查什么问题。第一轮用基础 Solver 的诊断，后续轮使用上一轮训练后的 Solver。

### 2. 根据失败构造任务

Designer 收到诊断摘要及公开的物体—容器兼容表，输出任务假设、引用的反馈编号、容器类型、物体类型与数量、物体初始位置和目标位置。每道任务的规格和反馈引用都会保存。

例如，观察到 Solver 在取放过程中反复查看背包后，Designer 可以提出：

> 在书架上放三张信用卡，要求把它们全部放入抽屉，考察 Solver 能否连续完成多次取放。

示例表达的是任务意图；实际候选必须使用兼容表中允许的类型和组合。构造器根据 ALFWorld 的 PDDL domain、类型规则和文本语法生成新环境，不要求 Designer 先挑选已有 FloorPlan，也不让模型直接编写 PDDL。当前范围是文本环境中的物体放置任务，每类容器一个实例，并非生成新的 3D 房间。

### 3. 规划、重放和形成监督

Host 检查场景规格与类型兼容性，确认初始状态尚未满足目标；然后让 TextWorld 调用 Fast Downward 搜索动作序列，再从初始状态在 ALFWorld 中真实重放，确认动作合法、目标谓词成立且环境返回成功。超过步数预算、无法重放或未通过其他检查的候选不进入 SFT。搜索超时只表示在当前时间预算内没有得到答案，并不证明任务无解。

对于通过验证的每个动作，保存 Solver 实际执行时会看到的任务、当前观察、动作历史、合法动作及剩余步数，并用 Planner 的下一步动作作为监督标签。轨迹与原始诊断、任务规格、假设和验证结果可相互追溯。Planner 能完成一道任务不代表 Solver 已经会做，因此它可以为 Solver 提供监督。

### 4. 训练 Solver 并进入下一轮

用 Transformers Trainer 和 PEFT 对 Solver 做 LoRA SFT，基础模型权重保持冻结。当前配置使用 Qwen3‑4B、rank 4 LoRA、每轮 1 个训练 epoch 和最多 20 个环境动作。多轮续跑入口将所有已验证任务的动作样本累积后训练，并从上一轮 adapter 继续。下一轮诊断使用更新后的 adapter，Designer 根据新反馈设计任务。

训练数据来自 Planner 已验证的轨迹；这条路径不训练 Designer，也不执行 Editor、Skills、P/K 修改选择、双分支奖励、GRPO 或 OPSD。仓库保留的相关代码属于早期方案。

## 实验设计

第一阶段先验证完整闭环：一轮目标生成 20 道有效任务，训练一次 Solver，比较训练前后的固定 ID/OOD 测试成绩。之后进行多轮实验，跟踪每轮诊断、有效任务数量、训练数据量和开发集表现。当前续跑从已有的 19 道有效任务种子轮开始，额外计划两轮；每轮目标 20 道，通过验证至少 8 道才开始该轮训练。

评估拆分按用途组织：

| 数据 | 用途 |
| --- | --- |
| Train-Diagnostic | 运行当前 Solver，得到出题反馈 |
| 合成任务 | Designer 基于反馈构造，由 Planner 和环境验证后用于 SFT |
| ID 开发集 | 每轮跟踪 Solver 表现，不参与出题或 SFT |
| ID / OOD 测试集 | 训练前与全部续跑结束后比较成功率 |

新的续跑分配会将种子轮的诊断和任务源场景一并排除，按源场景隔离诊断、开发和测试用途。合成任务由符号规则组装，不以原始 FloorPlan 作为基础场景。测试集不得进入 Designer 的诊断反馈或 SFT 数据。

正在运行的续跑使用较早的分配方式：1 个开发场景与种子轮诊断场景重复，第 3 轮诊断也复用了 1 个种子轮诊断场景，因此其开发集不完全独立。该运行复用了种子轮试验已经评测过的 ID/OOD 测试池；在剩余两轮中该池只用于最终评价，因此结果仍应与完全未用于此前试验的测试集区分。

### 关键对照

比较两组：

1. **失败引导出题**：Designer 看真实诊断反馈，再构造训练任务。
2. **随机出题**：使用相同的场景构造规则、Planner 和验证流程，随机生成任务，训练同一初始 Solver。

两组应匹配有效任务数量、Solver SFT 步数与训练设置，记录生成尝试数、Planner 时间和总环境交互成本；尽量匹配任务长度、物体数量和目标数量，避免难度分布差异掩盖出题反馈的作用。用相同诊断池和独立测试集，多个随机种子重复，比较训练前后 ID/OOD 成功率变化。随机出题对照是计划中的实验，目前不能用已有单组结果代替。

进一步分析可比较真实失败反馈与不提供失败细节的 Designer，以及不同轮次训练前后的失败类别、有效任务生成率、Planner 轨迹长度和环境成本。若反馈引导组提升更大，且收益能在多种子和独立场景上复现，就支持“失败反馈有助于选择训练任务”；如果两组接近，则需要分析生成任务是否真的覆盖了失败行为。

## 当前证据与范围

已验证的链路包括 Qwen3‑4B 提出部分场景规格、规则组装 PDDL 场景、Planner 求解与 ALFWorld 重放，以及一次 Solver LoRA SFT。后续多轮运行正在进行，尚无完整对照结论。生成规格中包含反馈引用，可以追踪出题依据；目前没有自动证明每道题与被引用失败存在因果关联。

与 CoEvolve 和 Explorer-Zero 的共同点是利用环境与可验证反馈产生训练数据。这里研究的具体对象是：**当前 Solver 的失败反馈如何影响 Designer 构造任务，以及这些任务经过 Planner 监督后是否比随机任务更能提升 Solver**。任务合成、规划器监督和 LoRA SFT 本身均有已有工作；方法贡献需要由反馈驱动出题的对照实验来支持，而不是仅凭模块组合宣称。
